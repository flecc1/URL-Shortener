# ТЗ: URL Shortener v1 (без БД, in-memory, роутинг через http.HandleFunc)

Уровень: соответствует главам 6–7 (методы, интерфейсы, struct embedding), без БД и без generics.
Роутинг — на классическом `http.HandleFunc` (работает в любой версии Go, без паттернов Go 1.22+). Метод и `{id}` из пути разбираются вручную внутри обработчиков.

## Функциональные требования

### Сократить ссылку
- `POST /shorten`
- Тело запроса: `{"url": "https://example.com/some/very/long/path"}`
- Ответ (201): `{"id": "abc123", "short_url": "http://localhost:8080/abc123", "original_url": "...", "created_at": "..."}`
- Сгенерировать короткий уникальный код (6–8 символов, буквы+цифры)
- Провалидировать, что url — валидный URL (схема http/https, есть хост)
- Обработчик должен сам проверить `r.Method == "POST"`, иначе вернуть 405 Method Not Allowed

### Редирект по короткой ссылке
- `GET /{id}`
- Если id существует — 302 Found с `Location: <original_url>`
- Если не существует — 404 Not Found
- `{id}` достаётся из `r.URL.Path` (например, через `strings.TrimPrefix(r.URL.Path, "/")`)

### Получить информацию о ссылке (без редиректа)
- `GET /shorten/{id}`
- Ответ (200): `{"id": ..., "original_url": ..., "created_at": ..., "access_count": N}`

### Обновить оригинальный URL
- `PUT /shorten/{id}`
- Тело: `{"url": "новый URL"}`
- 200 при успехе, 404 если id не найден, 400 при невалидном URL

### Удалить короткую ссылку
- `DELETE /shorten/{id}`
- 204 при успехе, 404 если не найдено

### Статистика переходов
- `GET /shorten/{id}/stats`
- Ответ: `{"id": ..., "access_count": N, "created_at": ..., "last_accessed_at": ...}`
- `access_count` увеличивается при каждом успешном `GET /{id}` (редиректе), не при обращении к `/stats` или `/shorten/{id}`

## Структура роутинга (важно из-за старого способа)

Так как `http.HandleFunc` не различает методы и не парсит `{id}` из пути сам — понадобится примерно такая раскладка обработчиков:

```go
http.HandleFunc("/shorten", shortenHandler)   // только POST /shorten
http.HandleFunc("/shorten/", linkHandler)     // GET/PUT/DELETE /shorten/{id} и /shorten/{id}/stats
http.HandleFunc("/", redirectHandler)         // GET /{id}
```

Внутри `shortenHandler` — проверка `r.Method == "POST"`.
Внутри `linkHandler` — нужно:
1. Отрезать префикс `/shorten/` от `r.URL.Path`, чтобы получить остаток пути
2. Проверить, не заканчивается ли остаток на `/stats` (через `strings.HasSuffix` или `strings.TrimSuffix`) — если да, это запрос статистики, а не обычный GET/PUT/DELETE
3. Дальше разветвление по `r.Method` (`switch r.Method { case "GET": ...; case "PUT": ...; case "DELETE": ... }`)

Внутри `redirectHandler` — путь `r.URL.Path` уже и есть `{id}` (без слэша в начале), но не забудь исключить случай `id == ""` (запрос на корень `/`), иначе будет ложный поиск пустой строки в хранилище.

## Требования к реализации

**Хранилище:** структура вроде `URLStore`, инкапсулирующая `map[string]*URLRecord` + `sync.RWMutex` (конкурентный доступ — это ещё не каналы/горутины из недель 7-8, но `sync.Mutex` тут естественно появится, можно уже потрогать)

**Интерфейс:** вынеси хранилище за интерфейс, например:
```go
type Storage interface {
    Create(url string) (*URLRecord, error)
    Get(id string) (*URLRecord, error)
    Update(id, url string) error
    Delete(id string) error
    IncrementAccess(id string) error
}
```
Это даст практику именно интерфейсов (глава 7) — хендлеры работают с `Storage`, а не с конкретной мапой, и заменить мапу на что-то другое (в т.ч. будущую БД на неделе 6) станет проще.

**Ошибки:** единый формат JSON-ошибки, например `{"error": "url not found"}`, обёртывай через `fmt.Errorf` + `errors.Is`, если завяжешь на неделю 3.

**Валидация URL:** `net/url.ParseRequestURI` + проверка `Scheme` и `Host`.

**Генерация id:** можно `crypto/rand` + base62-алфавит, либо простой counter+hash — не усложняй сверх меры на этом этапе.

## Что НЕ нужно в v1
- БД (это неделя 6, отдельная итерация)
- Аутентификация/пользователи
- Rate limiting
- TTL/истечение ссылок (можно оставить как идею на бонус)
- Роутинг Go 1.22+ (`http.ServeMux` с паттернами) — можно переписать на него отдельным упражнением уже после того, как всё заработает на `http.HandleFunc`

## Бонусные пункты (если останется время/интерес)
- Кастомный alias (`{"url": "...", "custom_id": "mylink"}`)
- Простой TTL с фоновой очисткой (уже намёк на горутины, но не обязательно сейчас)
- После того как всё заработает — переписать роутинг на `http.ServeMux` с паттернами (Go 1.22+) как отдельное сравнительное упражнение

## Оценка времени

Учитывая темп (~1–1.5 часа в будни, посвободнее в выходные) и что это идёт после глав 6-7:

- Проектирование структур/интерфейса + `POST /shorten` и `GET /{id}` (ядро) — 2–3 часа
- Ручной разбор метода/пути в `linkHandler` (`GET/PUT/DELETE /shorten/{id}` и `/stats`) — здесь уйдёт чуть больше времени, чем при новом роутинге, из-за ручного парсинга строк — 2.5–3.5 часа
- Статистика + валидация + обработка ошибок аккуратно — 1.5–2 часа
- Тесты (можно простые, не обязательно табличные ещё) + README — 1.5–2 часа

**Итого: ~7.5–10.5 часов**, то есть чуть больше недели в этом темпе — по-прежнему укладывается в недели 4-5, но с небольшим запасом стоит не откладывать начало кодинга до полного прочтения главы 7.

Скидывать код стоит по кускам (например, сначала структуры + интерфейс, потом хендлеры) — так проще давать фидбек по ходу, чем разбирать всё разом в конце.

Как начать писать
Сначала models/url.go — просто структура, без логики
Потом storage/storage.go — интерфейс (просто сигнатуры методов, без тел)
Потом storage/memory_storage.go — реализация интерфейса
Потом handlers/handlers.go — обработчики, принимающие storage.Storage как зависимость
В конце main.go — собираешь всё вместе
